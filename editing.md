# Editing the site from the browser

This repository ships a small editor for its own content: a page at **http://localhost:4321/edit**
that lists every entry, edits text and photos as blocks, opens the GPX routes in the route tool,
keeps the summit registry and the views computed from it, and writes everything back to the files
it came from.

It is a **development tool**. It exists only while `npm run dev` is running on your machine:
the page is not generated by `npm run build` (not in `dist/`, not in the sitemap, not in any
bundle), its API only answers requests coming from this computer, and nothing about it is
deployed. There is no login because there is nothing to log into.

```bash
npm run dev
# then open http://localhost:4321/edit
```

---

## What it is good for

| Task | Where |
| --- | --- |
| Create an ascent, a news post or a project | **Nueva entrada**, in the top bar or in each collection |
| Write or fix a post, section by section | **Contenido** tab of an entry |
| Drop photos in, choose grid / carousel / single, captions, where they sit on the route | **Contenido** and **Fotos** tabs |
| Title, date, mountain, altitude, coordinates, tags, hero image, GPX files | **Datos** tab |
| Mark waypoints on the route, stitch, trim or clean a GPX and write it back | **Ruta** tab, and **Rutas GPX** |
| Say which summits an outing reached, or that it was an attempt | **Datos** tab of an ascent |
| Add a summit to the registry, move it on the map, give it photos from the top | **Cumbres** |
| See which summits have a panorama, which went stale, and recompute one | **Cumbres**, and each summit's **Panorama** tab |
| Create, rename or delete an entry | **Contenido** (the list) |
| Translate a post into English, or mark a hand-written translation as current | buttons in the entry's top bar |
| See the photo library, what uses each file, and what nothing uses | **Fotos** |
| Edit the front page and the CV, in either language | **Sitio**, or the *Páginas* section of the list |
| Replace the profile photo, the CV PDF or the favicon | **Sitio → Archivos del sitio** |
| Broken photo paths, missing GPX files, posts without a description, stale translations | **Revisión** |
| Review the diff of what you changed and commit it | **Cambios** |

Everything is in Spanish, like the content it edits.

```
┌──────────┬──────────────────────────────────────────────────────────┐
│ Contenido│  Título de la entrada            [● Guardar] [Traducir] │
│ Sitio    ├───────────────────────────────┬──────────────────────────┤
│ Cumbres  │ Contenido Datos Ruta Fotos    │  vista previa de la      │
│ Fotos    │                               │  página real             │
│ Rutas GPX│ ───────────────────────────   │                          │
│ Cambios  │  bloques del post             │  (/ascents/<slug>)       │
│ Revisión │                               │                          │
│          │                               │                          │

│ 3 sin    │                               │                          │
│ guardar  │                               │                          │
└──────────┴───────────────────────────────┴──────────────────────────┘
```

The right-hand panel is the real page from the dev server, not an approximation. Saving
reloads it (Astro's own hot reload usually gets there first). `Vista previa` in the top bar,
or the × in the panel's own bar, hides it when you want the full width for writing.

**Saving is always explicit: `⌘S` / `Ctrl+S`, or the Guardar button.** The button glows
while there are unsaved changes, and leaving the entry (or closing the tab) asks first.

## The four collections

The list groups everything the site is made of; the pills above it narrow the view to one group.

| Group | Files | New entries | Notes |
| --- | --- | --- | --- |
| **Ascensos** | `src/content/ascents/` | yes | the only one with the **Ruta** tab |
| **Noticias** | `src/content/blog/` | yes | |
| **Proyectos** | `src/content/projects/` | yes | `category` is the three-value list the URLs use |
| **Páginas** | `src/content/pages/` | no — they are tied to the site's own routes | the front page (`home`) and the CV (`cv.mdx`) |

**Nueva entrada** (top bar, or the button on each group) asks for the collection, the title, the
slug and the date in one dialog, shows the URL the page will get, writes the file with the
collection's skeleton and opens it.

There is a fifth thing the site is made of, and it is not a post: the **summit registry**
(`src/content/summits/`), which has its own view — see *Las cumbres* below.

Every entry is edited the same way, whichever group it belongs to — the editor only adds the
**Ruta** tab when the collection is `ascents`, and only offers the fields its schema has.

### The front page and the CV

`home.md` is the intro paragraph of the front page; its greeting, title and subtitle are
frontmatter fields, so they are in the **Datos** tab. `cv.mdx` is the CV, written with the
components `<TimeLineGroup>`, `<TimeLine>` and `<Columns>`: the block editor keeps each
component whole — one card per timeline group — so you can edit a job or a degree without
touching the rest. Headings are their own cards, and the **Archivo** tab is always there for
the structure itself.

The **Sitio** view puts both pages (and their English versions) in one place, together with the
files the templates point at: the sidebar photo, `cv.pdf`, the favicon, the flags.
**Reemplazar** uploads a new file over one of them, *keeping the same name and extension*,
because the `.astro` components refer to it by path — the previous file goes to the backups.
Changing the path itself is a code change, so the editor does not do it.

## Editing the text: blocks

The body of a post is shown as a list of cards. Each paragraph, heading, list, table or code
block is one card; a photo group is one card too.

- **Reorder**: drag a card by its ⠿ handle, or use the ↑ ↓ buttons. The thin line between two
  cards is where it will land.
- **Split**: the `⤵` button in a text card's toolbar cuts it in two at the cursor.
- **Insert**: the buttons at the end of the list add a text, gallery or carousel card; dropping
  image files between two cards inserts a photo card right there.
- **Markdown still rules**: the small toolbar (H2, H3, **B**, *I*, lists, quote, `code`, `$math$`,
  links) only writes the Markdown for you. Anything Markdown or MDX can do, you can type.
- **What counts as one card**: a paragraph, a list, a table, a fenced code block, a `$$…$$`
  block — and an MDX or HTML element with everything inside it, however many lines it spans.

### Why blocks do not disturb the file

Each card remembers the exact source it came from and gives it back untouched unless you edit
it. The same is true of the frontmatter: a key you did not touch is written back character for
character. **Opening an entry and saving it without editing anything leaves the file byte for
byte identical** — so the editor never produces a diff full of reformatting noise.

The **Archivo** tab is the whole file in a textarea, for anything the form cannot express
(MDX components, raw HTML, a table you would rather paste). What you type there is parsed back
into the other tabs as you go.

## Photos

Photo cards are the editor's view of what `src/plugins/remark-media.mjs` understands:

| Card setting | Markdown it writes |
| --- | --- |
| Foto suelta / Automático | the images as a plain paragraph — one becomes a figure, several a row |
| Galería + columnas + proporción | `:::gallery{cols=2 ratio=1/1}` … `:::` |
| Carrusel + proporción | `:::carousel{ratio=3/2}` … `:::` |
| Pie de grupo | `caption="…"` on the block |
| Pie de foto | the image's title: `![alt](foto.jpg "pie")` |
| Ubicación | the `#` fragment: `#km=5.8`, `#time=12:41`, `#-33.75,-70.10`, `#off` |

**Adding photos.** Drop files on a photo card, on the gap between two cards, or use the
upload box in the **Fotos** tab. They are written to
`public/assets/img/posts/<slug>/`, which is the folder a relative path in a post resolves
against, and inserted with that relative path. A name that already exists is never
overwritten: the new file becomes `name-2.jpg`.

**Where a photo sits on the route map.** The dropdown on each photo covers the four ways
`src/lib/photos.ts` accepts, and **Fotos → Ubicar…** opens a map with the post's track drawn
on it so you can click the spot; that writes the coordinates form. Leave it on *Automático*
to use the photo's EXIF data instead, which is what `npm run photos` collects (the **Leer
EXIF** button runs it).

> If `PUBLIC_MEDIA_BASE_URL` is set, the site reads photos from that host. The editor still
> writes uploads into the repository (so `npm run photos` can read their EXIF) and says so in
> a warning — remember to upload them to that host as well.

## Routes (GPX)

The **Ruta** tab of an ascent shows the same route card as the published page — map,
elevation profile, days, stats — in the route tool's editable mode.

- **Marking points**: press *Marcar*, click the track to add a point, click a point to edit or
  delete it. Points are saved into the entry's `waypoints:` frontmatter (name, kind, lat, lon,
  altitude, note) when you press **Guardar marcas en la entrada** and then save the entry.
- **Points that come from the .gpx file itself** cannot be removed by the frontmatter — the
  entry can only add to them. If you delete or move one, the editor says so and points you at:
- **Escribir el GPX…**: writes the track as you see it — the files stitched into one, with every
  mark — to a `.gpx` in `public/`, and points the entry's `route:` at that single file. The
  previous file is copied to `.editor-local/backups/` first.
- **Herramientas del track** (same tab): trim a range of points, shift every timestamp by N
  minutes (a camera or watch set to the wrong timezone), thin the points to a minimum spacing
  (smaller files), drop heart rate, drop the times. These only change the track in memory —
  nothing touches the disk until you use *Escribir el GPX…*, and *Recargar del disco* or
  *Deshacer todo* brings the files back as they are.
- **Several files**: add them in **Datos → Ruta GPX** or in the Ruta tab; they are stitched in
  chronological order, exactly as the site does it at build time.

The **Rutas GPX** view does the same for the repository's `.gpx` files without an entry:
tick one or more to analyze them, see which posts use each file, mark points, and save.

## Las cumbres

`src/content/summits/` is one small YAML file per summit of the log — name, height, coordinates,
its OpenStreetMap node, and whether the view from its top is worth computing. It is what ties the
log together: a post names its summits in `summits:`, and from the registry come the summit's own
page, its pin on the map, its silhouette in *mis cumbres a escala*, and the panorama tab of every
post that climbed it. A summit climbed three times is one file with three ascents.

The **Cumbres** view lists the registry from highest to lowest, each row saying at a glance what
that summit has:

| Chip | Meaning |
| --- | --- |
| `3 ascensos` / `sin ascensos` | how many posts name it in `summits:` |
| `panorama` | the view from the top is computed and current |
| `panorama viejo` | the YAML file was edited after the panorama was computed |
| `panorama movido` | the panorama was computed from coordinates that are no longer these |
| `sin calcular` | `panorama: true`, but nothing has been computed yet |
| `fuera de alcance` | north or east of 0°, where `scripts/panoramas.mjs` does not go |
| `contorno` / `sin contorno` | whether it is in `src/data/profiles.json`, the to-scale chart |
| `2 fotos` | photos taken from the top |

Opening one gives the same three-pane editor a post gets, with the summit's real page on the
right:

- **Datos** is the form for the file: name, height, the coordinates (with the map picker), the
  zone, the OSM node, Wikidata, the timezone, and **Calcular el panorama**, which is the
  `panorama:` switch the script reads. The photos taken from the top are edited here too — a
  path, a bearing (degrees from north, where the camera points) and a caption; the bearing is
  what pins the photo to the right place on the panorama's ruler.
- **Panorama** is what the scripts left behind: when it was computed, the terrain mesh and the
  viewshed overlay as images, the outline for the chart, and the posts that climbed this summit.
- **Archivo** is the YAML itself.

**Computing is explicit, because it is slow.** A panorama reads the elevation model and asks
Overpass for the peaks, glaciers, towns and lakes of the whole region: minutes for the first
summit of a zone, less afterwards from the cache. So nothing runs on save — the editor only
tells you the panorama is out of date and offers the button:

| Button | What it runs |
| --- | --- |
| **Calcular el panorama** (one summit) | `npm run panoramas -- <id>` |
| **Calcular N panorama(s)** (the list) | `npm run panoramas` — the ones marked `panorama: true` with nothing computed |
| **Perfiles** | `npm run profiles` — every summit's outline, seconds each |

Both write into the repository (`src/data/panoramas/`, `src/data/profiles.json` and
`public/assets/panoramas/`), and those files are committed, so they show up in **Cambios** like
anything else.

**Creating and deleting.** *Nueva cumbre* asks for the name and the file name — the file name is
what posts write in `summits:` and the URL of its page — and starts it at zero height and zero
coordinates, to be filled in with the map. Deleting moves the file *and* its computed panorama
to the trash, and warns first about the posts that name it: a `summits:` pointing at a file that
is not there **fails the build**, so the reference has to go too. There is no rename, for the
same reason — the id is written in the posts and in the names of the computed files.

## Frontmatter (the Datos tab)

The form mirrors the zod schemas in `src/content/config.ts`, per collection — so `category`
for a project is the three-value list the URLs use, an ascent gets mountain/altitude/
coordinates/route/timezone, and `pages` only gets its own few fields. Extras:

- **Cumbres** (an ascent) is a picker over the registry, not a free-text field: the id has to
  match a file in `src/content/summits/` or the build fails, so the list offers what exists,
  shows each one's name and height, and flags an id the registry does not have. Several summits
  mean a traverse, in the order given. **Intento** next to it marks an outing where the summit
  was not reached: the summits above become the ones attempted, and the route's high point is
  labelled as such.
- **Coordenadas → Mapa** picks the latitude/longitude for the ascents map by clicking. On a
  summit of the registry the same control writes `lat`/`lon` instead.
- **Imagen de portada → Elegir…** browses `public/assets/img/headers` and the post photos, or
  uploads a new one, and writes the public path the layouts expect.
- **Tags** suggests every tag already used on the site.
- Any key the form does not know about is listed at the bottom and left alone.

## Translations

A post's English version lives at `src/content/<collection>/en/<slug>.md` and is edited exactly
like the original (the chip in the list — `EN ✓`, `EN ⟳`, `EN ✎`, `sin EN` — opens it).

- The **sin EN** chip in the list offers both ways: translate with Claude, or start from a copy
  of the Spanish file to translate by hand (that copy has no `translationHash`, so
  `npm run translate` will never overwrite it).
- **Traducir** on a Spanish entry runs `npm run translate -- <file>`: it needs
  `ANTHROPIC_API_KEY` (see `.env.example`). The output streams into the dialog.
- **Marcar al día** on an English entry runs `npm run translate -- --stamp`, which records the
  Spanish file's hash so the translation counts as current.
- **Quitar** next to `translationHash` in the Datos tab turns the file into a hand-written
  translation that `npm run translate` will never overwrite.

## Review and commit

**Revisión** runs the checks that otherwise only bite at build time: photos and GPX files that
do not exist, entries without a description or a date, translations that drifted, and photos no
entry mentions (with a one-click move to the trash). It checks the registry too — a `summits:`
pointing at a file that does not exist (which fails the build), a summit whose panorama was never
computed or no longer matches its file, a missing terrain or viewshed image, a summit absent from
the to-scale chart, and a summit photo whose file is not there or that has no bearing. Each one
names the command that fixes it. **Build completo** runs `npm run build`, which is the real
verdict.

**Cambios** is `git status` with a diff viewer: tick the files, write a message, commit.
It never pushes — do that yourself when you are happy with the commit.

---

## Nothing is deleted, nothing is overwritten blindly

- Every write first copies the previous content to `.editor-local/backups/<path>.<timestamp>.bak`.
- Every delete is a **move** to `.editor-local/trash/<timestamp>/<path>`.
- `.editor-local/` is gitignored. Clear it whenever you like — nothing depends on it:
  ```bash
  rm -rf .editor-local
  ```
- If a file changed on disk after the editor loaded it (git checkout, `npm run translate`,
  another tab), the save is **refused** and you are asked whether to overwrite.
- Unsaved work is also mirrored into the browser's `localStorage`; if the tab dies, reopening
  the entry offers the draft back.

## How it is put together

| Path | What it is |
| --- | --- |
| `editor/vite-plugin.mjs` | Mounts the API on the dev server. `apply: "serve"` ⇒ never part of a build. |
| `editor/server/*.mjs` | The API: content, the summit registry, media, GPX, git, npm tasks, checks. Node only. |
| `src/pages/edit/[...path].astro` | The page. `getStaticPaths()` returns `[]` unless `import.meta.env.DEV`, and the interface is loaded by an `is:inline` dynamic import, so the build produces nothing. |
| `src/editor/*` | The interface (browser). `boot.ts` is the entry point, `views/` has one file per view. |
| `src/styles/editor.css` | Its stylesheet. Every class is prefixed `ed-`. |

The editor deliberately **reuses the site's own code** rather than reimplementing it:
`src/lib/gpx-core.ts` for parsing, stitching, analysis and writing GPX, `src/lib/route-card.ts`
and `src/scripts/route-map.ts` for the route card and its map, `src/lib/photos.ts` for placing
photos on a route, `src/lib/media.mjs` for resolving photo paths. What you see while editing is
what the page will render, and a change to the site's behaviour reaches the editor for free.

Two things worth knowing when working on the editor itself:

- The interface hot-reloads like any front-end file. **The API (`editor/server/*.mjs`) is loaded
  once by the dev server: restart `npm run dev` after changing it.**
- The API is plain Node with no dependencies. Requests from anywhere but loopback get a 403, and
  every path is resolved and checked to be inside the repository before anything is read or
  written; uploads are restricted to image and `.gpx` extensions, and the npm tasks it can run
  are a fixed list of six, each saying whether its arguments are content files (checked to be
  inside the repository) or summit ids (a bare name, never a path).

## Adding a field

1. Add it to the collection's zod schema in `src/content/config.ts` (the site's source of truth).
2. Add it to `FIELDS` in `src/editor/schema.ts` — `type` picks the control.
3. If it needs a format of its own on the way out, give it a case in `emit()` in
   `src/editor/frontmatter.ts` (that is where `tags: ['a']`, the `route:` list and the
   `waypoints:` and `photos:` maps are written in the style the existing files use), and put it
   in `KEY_ORDER` — or `SUMMIT_KEY_ORDER`, for a key of the registry — so a file that does not
   have it yet gets it in the right place.

A summit file is not frontmatter but the same shape, so the same class reads and writes it, with
its own key order. Two things it does for those files in particular: plain text stays unquoted
(`region: Santiago · Precordillera`, the way they are written by hand) unless the value could be
read as something else, and a comment under a key — the commented photo example in
`provincia.yaml` — survives an edit to the key above it.
